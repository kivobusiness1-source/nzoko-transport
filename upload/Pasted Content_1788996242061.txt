PROMPT — NZOKO TRANSPORT V2 ULTRA
MODULE COMPLET DE SUIVI GPS DES BUS
NEON + POSTGRESQL + PRISMA + NEXT.JS + PWA

Tu travailles sur le projet NZOKO TRANSPORT.

OBJECTIF PRINCIPAL
==================

Je veux ajouter au projet un système professionnel de suivi GPS en temps réel des bus.

Le GPS doit provenir du smartphone du chauffeur.

Le chauffeur possède un téléphone connecté à Internet.
Son smartphone récupère sa position GPS.
Cette position est envoyée de manière sécurisée au backend.
Le backend enregistre les données dans Neon PostgreSQL.
Le système temps réel transmet les nouvelles positions aux interfaces autorisées.
L'administrateur de l'agence peut voir ses bus sur une carte sans actualiser la page.

IMPORTANT :
- La base de données utilisée est NEON PostgreSQL.
- Prisma ORM doit être utilisé.
- Ne pas utiliser Supabase.
- Ne pas remplacer Neon par une autre base.
- Ne pas supprimer les fonctionnalités existantes de NZOKO.
- Le système doit être compatible avec Next.js.
- L'application chauffeur doit fonctionner sur smartphone.
- L'interface doit être PWA/mobile-first.
- Le système doit être sécurisé.
- L'architecture doit pouvoir évoluer vers plusieurs agences et plusieurs centaines de bus.

14. FRÉQUENCE GPS
==================================================

Implémente une fréquence intelligente.

Lorsque le bus roule :

≈ toutes les 5 à 10 secondes.

Lorsque le bus est arrêté :

réduire la fréquence.

Lorsque le trajet est terminé :

arrêter le tracking.

Ne pas envoyer inutilement des milliers de requêtes.

Prévoir un mécanisme de throttling côté client ET serveur.

15. OFFLINE GPS
==================================================

Le téléphone peut perdre Internet.

Dans ce cas :

NE PAS perdre les positions.

Stocker temporairement les positions localement.

Utiliser IndexedDB pour la file d'attente locale.

Lorsque Internet revient :

envoyer les positions restantes au serveur.

Chaque position doit avoir un timestamp original.

Le serveur doit distinguer :

recordedAt
receivedAt

Ainsi, l'historique reste cohérent même après une coupure Internet.
